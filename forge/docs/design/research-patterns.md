
# State of the art (Oct 2026): designing a portable, multi-model AI engineering team inside Claude Code

Research foundation report. All claims below are tied to primary sources I fetched directly (URL given); where a figure comes only from secondary coverage I say so. Local Anthropic-authored files bundled with Claude Code 2.1.296's `claude-api` skill (`shared/cost-optimization.md`, `shared/model-migration.md`, `shared/agent-design.md`, `shared/tool-use-concepts.md`) are cited as "[bundled skill]"; they mirror platform.claude.com guidance but are not public URLs.

**Operating facts as of 2026-10-11 (from the bundled skill's model table and code.claude.com docs):** Fable 5.1 `claude-fable-5-1` $10/$50 per MTok; Opus 5.5 `claude-opus-5-5` $4/$20; Sonnet 5.5 `claude-sonnet-5-5` $2/$10; Haiku 5.5 `claude-haiku-5-5` $0.10/$0.50 (≤100K-token prompts). All have 1M context and five effort levels (`low`…`max`). Thinking cannot be disabled on Opus 5.5/Sonnet 5.5/Haiku 5.5/Fable. Claude Code aliases: `fable`, `opus` (→5.5), `sonnet` (→5.5), `haiku` (→5.5), `best`, and `opusplan` (Opus in plan mode, Sonnet for execution). Claude Code effort defaults: `high` except Opus 5.5 / Sonnet 5.5 / Haiku 5.5 → `medium` (https://code.claude.com/docs/en/model-config). Note the API default for Sonnet 5.5 is `high` (bundled skill) while Claude Code's is `medium`.

### Concrete recommendations extracted

**Workflows before agents; orchestrator-workers for unpredictable subtasks.** "Building effective agents" distinguishes workflows (predefined code paths) from agents (model-directed). Orchestrator-workers is for when "the subtasks can't be predicted in advance"; its canonical example is "coding tools that change many files". Routing's example is literally "sending simple questions to smaller models and hard ones to more capable models." Evaluator-optimizer is for when "evaluation criteria are clear and iterative refinement measurably helps." The three principles: simplicity, transparency (show planning steps), and a carefully designed agent-computer interface. On SWE-bench they "spent more time optimizing our tools than the overall prompt"; requiring absolute file paths eliminated a whole error class.

**Context isolation per subagent, condensed returns.** In the research system, subagents operate "with their own context windows" and return "condensed results rather than full transcripts." The lead "saves its plan to memory because the context window can be truncated." Sub-agents "may explore extensively but return a condensed summary, often 1,000–2,000 tokens" (context-engineering post). Claude Code subagents: "Each subagent runs in its own context window with a custom system prompt, specific tool access, and independent permissions"; a non-fork subagent "does not see your conversation history". Only the final text returns plus a token trailer (the docs' simulation: 6,100 tokens read, 420 returned).

**Teach the orchestrator to delegate and to scale effort to complexity.** The research post found vague delegation produced duplicated work; each subagent needs "an objective, an output format, guidance on tools and sources, and clear task boundaries." Explicit scaling rules: "Simple fact-finding uses one agent with 3-10 tool calls. Direct comparisons use 2-4 subagents. Complex research may use more than 10 subagents." Heuristics beat rigid rules; guardrails against runaway spawning.

**Token budget is the dominant performance variable.** On BrowseComp, "Token usage alone explained 80% of the variance"; multi-agent Opus-4-lead/Sonnet-4-workers beat single Opus 4 by 90.2% on an internal eval, but "Multi-agent systems use about 15× the tokens of chats", so only for high-value tasks.

**When NOT to use multi-agent (Anthropic's own words):** "Domains where all agents must share the same context", "Tasks with many dependencies between agents", "Most coding tasks, which have fewer truly parallelizable parts than research", and low-value tasks. Agent-teams docs repeat it: "For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective."

**Planner/generator/evaluator separation and a negotiated definition of done.** The Mar 2026 harness post: agents "confidently prais[e] the work" they produced, so a separate evaluator was required; the planner "stays high-level on technical details so that spec errors don't cascade downstream"; generator and evaluator negotiate a sprint contract "agreeing on what 'done' looked like for that chunk of work before any code was written" (Sprint 3 had 27 criteria); evaluator clicks through the running app with Playwright and "Any criterion below its hard threshold fails the sprint." Cost: solo Opus 4.5 run 20 min/$9 but the central feature didn't work; full harness 6 h/$200 and functional. "every component in a harness encodes an assumption about what the model can't do on its own" — remove components one at a time, not all at once; "Without the planner, the generator under-scoped."

**Clean-context handoff vs compaction.** Same post: compaction "summarizes history in place. The same agent continues, so context anxiety can persist"; "A reset provides a clean slate" but the handoff must carry enough state. Resets were essential on Sonnet 4.5 and dropped on Opus 4.5. Managed-agents post: "The resets had become dead weight" on Opus 4.5 — i.e., make resets a configurable harness policy, not a dogma. Nov 2025 harness post: compaction "doesn't always pass perfectly clear instructions to the next agent"; the fix is files + git: progress file + feature list (JSON chosen because the model is "less likely to inappropriately change or overwrite JSON files" than Markdown) + `init.sh`; "one feature at a time" is "critical"; each session starts by running `pwd`, reading git log and progress files, picking the highest-priority unfinished feature, starting the server and running a basic end-to-end test "before new work".

**Verify before claiming done.** Best-practices: "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available." Escalation ladder: in-prompt check → `/goal` (a separate small model re-judges the condition after every turn) → Stop hook as deterministic gate → "a verification subagent … has a fresh model try to refute the result, so the agent doing the work isn't the one grading it." "Have Claude show evidence rather than asserting success." Nov 2025 harness post: Claude "often marked features complete after unit tests or curl checks"; browser-automation E2E testing "as a human user would" fixed it. Fable 5.1 guidance [bundled skill]: "Separate fresh-context verifier sub-agents tend to outperform self-critique"; add "Before reporting progress, audit each claim against a tool result from this session" — "in testing this nearly eliminated fabricated status reports". Sonnet 5.5 and Haiku 5.5 at `low` (and Haiku at `medium`) "sometimes report a code change as done without a check that exercises it" — Anthropic supplies a system-prompt paragraph requiring a real test/build/type-check run.

**Adversarial review, with scope discipline.** Best-practices: a reviewer subagent "sees only the diff and the criteria you give it, not the reasoning that produced the change." Caveat: "A reviewer prompted to find gaps will usually report some, even when the work is sound… Tell the reviewer to flag only gaps that affect correctness or the stated requirements." Writer/Reviewer in separate sessions because "A fresh context improves code review since Claude won't be biased toward code it just wrote."

**Context is the binding constraint; clear often.** "Most best practices are based on one constraint: Claude's context window fills up fast, and performance degrades as it fills." "After two failed corrections, `/clear` and write a better initial prompt"; "A clean session with a better prompt almost always outperforms a long session with accumulated corrections." Spec-first: interview the user, write SPEC.md, "Once the spec is complete, start a fresh session to execute it." Plan mode is for multi-file or unfamiliar changes: "If you could describe the diff in one sentence, skip the plan."

**Right-altitude prompts, minimal toolsets, progressive disclosure.** Context-engineering post: find "the smallest set of high-signal tokens"; "If a human engineer can't definitively say which tool should be used" neither can the agent; Claude Code loads CLAUDE.md up front and uses glob/grep just-in-time; compaction should keep "architectural decisions, unresolved bugs, and implementation details" and discard "redundant tool outputs"; tune compaction "by maximizing recall … then improve precision."

**Current-model prompting shifts that affect an orchestrator design [bundled skill, Fable 5.1 sections]:** "Lower effort settings - including `low` - still perform very well on Claude Fable 5.1, often exceeding the `xhigh` or even `max` performance of previous models." "Prompts and skills written for prior models are often too prescriptive for Claude Fable 5.1 and *reduce* output quality… prefer stating the goal and constraints over enumerating the steps." "Parallel sub-agents are dependable on Claude Fable 5.1 - instead of suppressing delegation… use sub-agents frequently"; asynchronous delegation beats spawn-and-block. "Give it a memory surface… even a plain `.md` file… Store one lesson per file." Autonomy prompt for unattended runs ("You are operating autonomously. The user is not watching…"). Avoid surfacing token countdowns (context anxiety). Scope prompt to stop unrequested refactors/test sprawl. Mid-turn harness notices placed after tool results can be read as prompt injection by Sonnet 5.5/Haiku 5.5 — keep harness notices in a separate system message.

**Claude Code multi-agent surfaces (https://code.claude.com/docs/en/agents):** subagents (delegated, summary back), agent view (background sessions), agent teams (experimental, disabled by default; shared task list + mailbox; "approximately 7x more tokens than standard sessions when teammates run in plan mode"; no worktree isolation; "Start with 3-5 teammates"; "Use Sonnet for teammates"), dynamic workflows (a JS script orchestrates dozens–hundreds of subagents; "intermediate results stay in script variables instead of landing in Claude's context"; can "adversarially review each other's findings"; `ultracode` keyword / `/effort ultracode`), `/batch` (5–30 worktree-isolated subagents). Ultraplan (cloud planning) **has been removed** (https://code.claude.com/docs/en/ultraplan). Subagent facts: nesting default 3 layers (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`), 20 concurrent (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`), frontmatter `model`/`effort`/`memory`/`isolation: worktree`/`skills`/`hooks`/`maxTurns`; model resolution order: per-invocation → frontmatter → `CLAUDE_CODE_SUBAGENT_MODEL` → main model; `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` pins all workers. Warning at startup when agent descriptions exceed 15,000 tokens.

### What the evidence says

**Long context degrades, non-uniformly, and distractors hurt.** Chroma: "models do not use their context uniformly; instead, their performance grows increasingly unreliable as input length grows." "Even a single distractor reduces performance relative to the baseline"; four distractors hurt more. "Across all models, we see significantly higher performance on focused prompts compared to full prompts" (LongMemEval: ~300 vs ~113K tokens). Counter-intuitively, "structural coherence consistently hurts model performance" (shuffled haystacks did better across all 18 models). Claude models tended to abstain rather than hallucinate. Lost in the Middle: >20-point drop from start to middle on 20-doc QA; adding documents past ~20 gave ≈1–1.5% for GPT-3.5/Claude-1.3; recommendation: rerank/truncate so relevant material sits early. Anthropic's framing: "Context, therefore, must be treated as a finite resource with diminishing marginal returns" and attention is "n² pairwise relationships."

**Why fresh context per phase beats one long context.** (1) Chroma focused-vs-full; (2) Claude Code best practices "clean session… almost always outperforms a long session with accumulated corrections"; (3) Anthropic harness-design: resets give "a clean slate" and avoid persistent "context anxiety"; (4) Cursor: "the need for periodic fresh starts to counter drift and tunnel vision"; (5) Ralph: one fresh window per task; (6) ACE-FCA: keep utilization "in the 40%-60% range"; (7) Fable 5.1 guidance: context anxiety appears "most often when the harness surfaces a remaining-token countdown". Important counter-evidence: Cognition argues splitting work across agents loses "implicit decisions" and produces conflicting outputs; their prescription is one linear agent plus a dedicated compressor. The reconciliation supported by both camps: reset at *phase boundaries* where a complete written artifact (spec/plan/handoff) carries the decisions, not mid-task; and do not run parallel implementers on interdependent work.

**Claude Code compaction mechanics (what survives).** From https://code.claude.com/docs/en/context-window and /memory: the summary "keeps: your requests and intent, key technical concepts, files examined or modified with important code snippets, errors and how they were fixed, pending tasks, and current work"; after compaction Claude Code re-reads project-root CLAUDE.md, "re-reads up to five of the files modified most recently and re-injects the skills you invoked" (capped at 5,000 tokens per skill); "The skill listing does not reload." You can steer compaction from CLAUDE.md ("When compacting, always preserve the full list of modified files and any test commands") and with `/compact <instructions>`; a `SessionStart` hook with matcher `compact` can re-inject critical context (https://code.claude.com/docs/en/hooks-guide). Thresholds are tunable: `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` (https://code.claude.com/docs/en/env-vars). The API's own client-side summarization prompt for Fable 5.1 [bundled skill] enumerates six must-keep items: difficulties and resolutions; options tried/set aside and why; everything decided/agreed/ruled out "stated exactly"; "exactly where things stand now"; anything open/promised; hard-to-reconstruct specifics (names, numbers, exact wording).

**The progress/status/handoff-file pattern (converged fields).** Primary sources that use it: Anthropic Nov 2025 (`claude-progress.txt` + `feature_list.json` + `init.sh`), Anthropic scientific computing (`CHANGELOG.md` as "the agent's portable long-term memory, acting as a sort of lab notes"; "The failed approaches are important—without them, successive sessions will re-attempt the same dead ends"; example entry "Tried using Tsit5 for the perturbation ODE, system is too stiff. Switched to Kvaerno5."), C compiler (READMEs + progress files "updated frequently with current status"; a running doc of failed approaches when stuck), Ralph (`IMPLEMENTATION_PLAN.md` as shared state between isolated iterations; `AGENTS.md` ≈60 lines of commands, "NOT a changelog or progress diary"), superpowers (a git-ignored per-plan ledger because "Conversation memory does not survive compaction"; per-task *brief* file + *report* file; implementer statuses DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED; "Ruling: <decision> — <why> — <cost if wrong>"), BMAD (story file "acts as the complete handoff package"), community kits (goal state, decisions with reasons, files touched, open loops, next action, verification, do-not-touch). Synthesized field list that every well-regarded source covers at least partially: **goal + scope; status/current step; done (with evidence: command + result); remaining (ordered, one "next action"); decisions with rationale; failed approaches / do-not-repeat; gotchas / do-not-touch; files touched; verification commands + expected output; open questions; environment/bootstrap command.** Guidance on form: JSON (or structured frontmatter) for machine-updated state the agent must not freely rewrite (Anthropic chose JSON for the feature list for exactly this reason); Markdown for narrative notes; write at task end, read at task start (Alook: "A handoff nobody updates is worse than none").

**Session bootstrap ritual (primary sources agree).** Anthropic Nov 2025: `pwd` → git log + progress file → pick highest-priority unfinished item → run `init.sh` and a basic E2E check before new work. Scientific computing: prompt is literally "Read CHANGELOG.md and pick up the next task"; rules such as "Never commit code that breaks existing passing tests." C compiler: fresh container each session; "will spend significant time orienting itself, especially on large projects" unless READMEs/progress docs are maintained.

**Parallel-worker coordination lessons.** C compiler: lock files in `current_tasks/` claimed through git; no orchestrator; "Merge conflicts are frequent, but Claude is smart enough to figure that out"; failure mode: "Every agent would hit the same bug, fix that bug, and then overwrite each other's changes"; CI added late because "New features frequently broke existing functionality"; a dedicated dedup agent because LLM code "often reimplemented existing functionality." Cursor: lock-based self-coordination collapsed to the throughput of 2–3 agents; without hierarchy "No agent took responsibility for hard problems"; an integrator role "created more bottlenecks than it solved"; "The harness and models matter, but the prompts matter more." Agent-teams docs: "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files."

### Extracted heuristics and evidence

**Planner quality dominates; executor can be cheaper — but only when there is something to hand off.** PEAR: weak planners hurt far more than weak executors. Aider: a strong reasoner describing the change plus a cheaper editor applying it beats the strong model alone. Anthropic's own multi-agent result (Opus lead, Sonnet workers). Counter-evidence (akitaonrails; Anthropic cost guidance): on a cohesive, single-chain task the orchestrator "pays for a plan, a handoff, and a merge that a single model gets for free - in every such case measured, the coordinator's model alone at lower effort came out ahead." Anthropic's measured verdict [bundled skill]: the orchestrator shape "buys something only when there is bulk to hand off - many independent pieces, ideally too many for one context window"; on such work it cost "about half as much as the frontier model solo, for a lower score."

**Effort is the first lever; "stronger model at lower effort" is real and must be benchmarked before cascading.** Opus 4.5: medium effort matched Sonnet 4.5's SWE-bench with 76% fewer output tokens. Opus 5.5 [bundled skill]: "at `medium` exceeds Claude Opus 5 at `high` on coding and knowledge-work evaluations." Sonnet 5.5: "scored higher at `medium` than Claude Sonnet 5 did at `high`, typically at under a fifth of the cost." Fable 5.1: "At `low`, Claude Fable 5.1 is often competitive with Opus and Sonnet on cost per task while performing better - evaluate low Fable effort against below-frontier usage before reaching for a cheaper model." Cost-optimization guidance: "Before building a multi-model cost cascade, measure the simpler alternative first - the most capable model at lower effort on the same tasks"; "one model means one cache namespace (caches are model-scoped, so a cascade forfeits cache reuse across its models)"; "Judge cost per completed task, not per request." Effort names do not map across models — re-sweep after every migration. Claude Code's July 2026 article: raise effort "if Claude skipped a file, didn't run tests, or didn't double-check"; pick a larger model "If Claude had the pertinent context, clearly tried, and was still wrong"; treat effort "as a general preference than a task-by-task decision"; smaller models suit "precisely described edits, mechanical changes, and questions about code already in context" and "specific execution instructions work better on smaller models." Claude Code costs page: "Sonnet handles most coding tasks well … Reserve Opus for complex architectural decisions or multi-step reasoning"; "For simple subagent tasks, specify `model: haiku`"; "Use Sonnet for teammates." `max` "may show diminishing returns and is prone to overthinking" (model-config).

**Cascade/escalation beats ex-ante classification when a verifier exists.** FrugalGPT and RouteLLM show large savings but need labeled training data. For coding, the cheap, robust version is Anthropic's measured "re-run failures at higher effort" policy: run everything cheap, re-run only failures at a higher setting — "this held the pass rate of running everything at the higher setting, or slightly beat it, for a little over half the cost." Superpowers encodes the same idea structurally (fix rounds 4–5 escalate to "a more capable model"). T2MO formalizes it: price failure escalation into cost per completed task.

**Advisor pattern (executor consults a stronger model) is fragile.** [bundled skill] "pays when the capability gap between the two models is wide and the executor actually consults. The consult rate is the fragile variable"; "asking the executor to recognize the hard cases itself demands the very judgment it's missing"; on Anthropic's coding benchmark the flagship pairing "landed about on the executor model's own effort curve."

**Task features that predict difficulty/cost (what to route on).**
- Strong structural predictors (2608.18280): `patch_lines_deleted`, `patch_num_hunks`, `patch_hunk_gap_mean` (scatter), repository scale/directory structure/naming ambiguity; patch + repo features alone reach AUC 0.861 for any-success. Prompt ambiguity features add signal mainly for mid-band tasks (top-5 contributor for 70.3% of mid-band tasks).
- Weak/unreliable signals: human expert difficulty ratings (2604.22750 — "only weakly aligns with actual token costs"); LLM self-assessment of difficulty (2511.18597 — systematic downgrade of Hard tasks; "relying solely on LLM judgments is not advisable"); model self-estimates of token cost (2604.22750).
- Better: hybrid of measurable constraints + numeric features ("rely on interpretable numeric models to anchor difficulty judgments in measurable constraints"); model-internal signals (probes/entropy) where available; and, pragmatically, the verifier outcome (cascade).
- Risk features are separate from difficulty and dominate routing for gating: reversibility ("hard-to-reverse actions (external API calls, sending messages, deleting data) can be gated behind user confirmation" — [bundled skill] agent-design); Claude Code auto-mode classifier blocks "scope escalation, unknown infrastructure, and hostile-content-driven actions" (best-practices); Fable guidance: "Before running a command that changes system state - restarts, deletes, config edits - check that the evidence actually supports that specific action." Cheaper models at low effort have a documented tendency to skip verification and stop early (Sonnet 5.5 / Haiku 5.5 sections), which argues for keeping security-sensitive, data-loss-prone, and cross-cutting work on the stronger tiers.
- The user's proposed features (cross-file blast radius, ambiguity, novelty, test coverage, security sensitivity, data-loss risk) are consistent with the evidence: blast radius ≈ patch scatter/hunks/dirs (strong); ambiguity (mid-band only); test infrastructure presence is a repo feature the paper includes but does not rank; security/data-loss are risk gates rather than difficulty predictors.

**Practical routing matrix the evidence supports (Oct 2026 lineup):**
| Work | Model / effort | Why |
|---|---|---|
| Spec, architecture, decomposition, ambiguous/novel problems, root-cause debugging, final review | Fable 5.1 (`high` default; `medium` for routine planning) | Planner quality dominates (PEAR); Claude Code guidance: hand Fable "ambiguous problems: root-cause investigations, outage debugging, and architecture decisions". |
| Implementation of a well-specified task touching several files | Opus 5.5 `medium` (or Fable `low` if measured cheaper per completed task) | Opus 5.5 medium > Opus 5 high; Fable `low` often competitive per task. |
| Routine implementation with exact file paths, tests, and small blast radius | Sonnet 5.5 `medium` | "strongest on multistep agentic coding in a real repository"; medium > Sonnet 5 high at <1/5 cost. |
| Mechanical edits, renames, log-filtering, summarization of tool output, bulk search | Haiku 5.5 `medium` (never `low` for anything that must verify) | Costs page; Haiku 5.5 effort guidance; low-effort verification gap. |
| Evaluator/verifier | Fresh-context subagent; at least the implementer's tier for correctness review; Fable for final gate on high-risk changes | Harness-design evaluator; "verifier sub-agents tend to outperform self-critique". |
| `/goal` evaluator | Small fast model (Haiku) | Docs: evaluation runs on the configured small fast model; cost "typically negligible". |

### Extracted recommendations
1. **External, mechanical verification first; LLM judgment last.** Rules-based (tests, type-check, lint, build exit codes) > visual (screenshots/Playwright) > LLM-as-judge. Self-correction without external feedback is unreliable (Huang et al.), and agents over-praise their own work (harness-design). OpenAI's harness enforces architecture with "custom linters and structural tests" (Fowler memo).
2. **Separate the evaluator from the generator, in a fresh context, with calibrated criteria and hard thresholds.** Harness-design evaluator; Claude Code adversarial-review subagent; Managed Agents graders; superpowers two-stage review; Cursor's judge. Calibrate with few-shot examples; give a rubric per dimension; allow "Unknown"; weight the dimensions the generator is weakest on (harness-design weighted design/originality higher).
3. **Define done before coding; make it checkable.** Sprint contract (harness-design), EARS acceptance criteria (Kiro), spec checklists "requirements are testable, and success criteria are measurable" (spec-kit), `/goal` conditions with "a stated check", Ralph "Clear completion criteria" (bad: "make it good"; good: enumerated verifiable conditions + `<promise>COMPLETE</promise>`), best-practices SPEC.md that "end[s] with an end-to-end verification step".
4. **Evidence, not claims.** "NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE" (superpowers): full command output in the current turn, exit code, red-green for regression tests, VCS diff; forbidden hedges ("should", "probably"). Anthropic's Fable prompt: "Only report work you can point to evidence for; if something is not yet verified, say so explicitly." Keep verification instructions when migrating to Fable 5.1 (bundled skill: "the Claude Opus 5 guidance to delete verification instructions doesn't apply here").
5. **Deterministic gates via hooks.** Prose in CLAUDE.md is advisory; "hooks are deterministic and guarantee the action happens" (best-practices). Use `TaskCompleted`/`Stop`/`SubagentStop` with exit 2 to block "done" until tests pass; `PreToolUse` to block writes to protected paths; `PostToolUse` to run formatters/linters and return `additionalContext`. Mind the 8-consecutive-block cap.
6. **Test ratchet and verifier quality.** "it is unacceptable to remove or edit tests" (Anthropic prompt, quoted by Osmani; Nov 2025 post insists tests must not be removed or edited); CI once regressions appear (C compiler); design test output for agents (short, greppable, sampled); use reference implementations/oracles where tests are weak.
7. **Scope the reviewer.** "Report gaps, not style preferences"; otherwise "Chasing every finding leads to over-engineering" (best-practices). Superpowers: minor findings are "logged as deferred"; after 5 fix rounds the controller adjudicates with a written ruling.
8. **Spec-driven development as the upstream gate.** Spec-kit's "power inversion" ("Specifications don't serve code—code serves specifications"), `[NEEDS CLARIFICATION]` markers, constitution gates with justified exceptions; Kiro's approval gates between requirements/design/tasks ("tasks derived from a design you did not read are tasks you approve without knowing what you agreed to"); test-first "NON-NEGOTIABLE". ACE-FCA: review plans, not generated code — "a bad line of a plan could lead to hundreds of bad lines of code."
9. **Evaluate the system itself with a small, real-failure-derived eval.** 20–50 tasks; regression suite ~100%; read transcripts; "grade outcomes, not paths"; harness assumptions must be re-tested per model generation (managed-agents: resets became "dead weight").

## Design implications for a Claude Code-hosted AI engineering team

Each decision names the strongest supporting sources.

1. **Topology: one orchestrator (Fable 5.1) + fresh-context worker subagents that return condensed results; not a free-form agent team by default.** — Building effective agents (orchestrator-workers for unpredictable, many-file coding); multi-agent research system (isolation, condensed returns); sub-agents docs; agent-teams docs (teams are experimental, ~7× tokens, no worktree isolation); Cursor (hierarchy beat flat self-coordination).

2. **Parallelize only independent, file-disjoint work; keep dependent chains in one worker.** — Cognition ("Actions carry implicit decisions"); Anthropic ("Most coding tasks… have fewer truly parallelizable parts"); Anthropic cost guidance (orchestrator pays only with "bulk to hand off"); akitaonrails counter-experiment; C-compiler duplicated-work failure; agent-teams "each teammate owns a different set of files"; `/batch` and `isolation: worktree` for the parallel case.

3. **Invest in the plan; planner quality matters more than executor quality.** — PEAR; ADaPT/IPIGuard; Aider architect/editor; harness-design ("Without the planner, the generator under-scoped"; planner stays high-level so "spec errors don't cascade"); ACE-FCA ("a bad line of a plan…").

4. **Scale process to task size with explicit rules (trivial → direct; medium → plan mode; large → spec + plan + tasks).** — Multi-agent research scaling rules (3–10 calls / 2–4 subagents / 10+); best-practices "If you could describe the diff in one sentence, skip the plan"; BMAD Quick Flow; spec-kit three entry points; Managed-Agents warning that harness components encode assumptions.

5. **Phase boundaries = context resets with a written handoff; compaction only inside a phase.** — Harness-design (resets vs compaction); best-practices "clean session… almost always outperforms"; Chroma focused-vs-full; Ralph one-task-per-window; ACE-FCA 40–60% utilization; managed-agents (resets configurable, since they became "dead weight" on a stronger model).

6. **Handoff document schema (fixed fields, written at phase end, read at phase start):** goal/scope; status; done with evidence; remaining with one explicit next action; decisions + rationale; failed approaches (do-not-repeat); gotchas/do-not-touch; files touched; verification commands + expected output; open questions; bootstrap command. Use JSON/frontmatter for machine-updated status, Markdown for narrative. — Anthropic Nov 2025 (progress file + JSON feature list + init.sh); scientific-computing CHANGELOG with failed approaches; Fable compaction summary's six must-keep items; superpowers brief/report/ledger; community handoff kits.
